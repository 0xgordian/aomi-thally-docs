An Aomi App is a Rust crate that the runtime loads as a plugin. You write the tools and a short system prompt. Aomi runs the model, the sessions, simulation and signing. Here you build `hello-aomi`, an App with one `greet` tool, and take it from an empty folder to live chats.

Prefer the browser? [build.aomi.dev](https://build.aomi.dev) can fork a working template into your GitHub account and deploy it without a local toolchain.

## Before you start

You need Rust 1.85 or newer (the SDK uses the 2024 edition), git, and a GitHub repository you can push to.

```bash
rustc --version
git --version
```

Install the toolchain. The `cli` feature builds `aomi-build`. `dev-runtime` adds `aomi-run`, which lets you chat with your App locally.

```bash
cargo install aomi-sdk --locked --features cli,dev-runtime
aomi-build --help
```

Neither binary has a `--version` flag. `--help` is how you confirm the install.

## Write the App

Three files. The folder name becomes your App's slug, so use kebab-case.

```bash
mkdir hello-aomi && cd hello-aomi && mkdir src
```

<Steps>
  <Step title="aomi.toml">
    Who the App is and where it ships:

    ```toml aomi.toml
    [app]
    name         = "hello-aomi"
    display_name = "Hello Aomi"
    platform     = "community"
    git          = "https://github.com/aomi-labs/community-apps"
    public       = true
    ```
  </Step>
  <Step title="Cargo.toml">
    The App compiles to a `cdylib`, and `aomi-sdk` must be pinned to the exact version the platform requires:

    ```toml Cargo.toml
    [package]
    name = "hello-aomi"
    version = "0.1.0"
    edition = "2024"

    [lib]
    crate-type = ["cdylib"]

    [dependencies]
    aomi-sdk   = "=5.1.1"
    schemars   = "1"
    serde      = { version = "1", features = ["derive"] }
    serde_json = "1"
    ```

    `5.1.1` is only an example and the required version moves often. Run `aomi-build sdk check` to read the current one, or `aomi-build sdk fix` to set it. Keep the leading `=`. A caret or a range gets the build rejected at activation.
  </Step>
  <Step title="src/lib.rs">
    One tool, a preamble, and the `dyn_aomi_app!` macro that registers them:

    ```rust src/lib.rs
    use aomi_sdk::schemars::JsonSchema;
    use aomi_sdk::*;
    use serde::Deserialize;
    use serde_json::{Value, json};

    #[derive(Clone, Default)]
    pub struct HelloApp;

    #[derive(Debug, Deserialize, JsonSchema)]
    pub struct GreetArgs {
        /// The name of the person to greet.
        pub name: String,
    }

    pub struct Greet;

    impl DynAomiTool for Greet {
        type App = HelloApp;
        type Args = GreetArgs;
        const NAME: &'static str = "greet";
        const DESCRIPTION: &'static str =
            "Use when the user wants a friendly greeting. Takes a name and returns a hello message.";

        fn run(_app: &HelloApp, args: GreetArgs, _ctx: DynToolCallCtx) -> Result<Value, String> {
            Ok(json!({ "message": format!("Hello, {}! Welcome to Aomi.", args.name) }))
        }
    }

    const PREAMBLE: &str =
        "When the user asks to be greeted, call the greet tool with their name.";

    dyn_aomi_app!(
        app = HelloApp,
        name = "hello-aomi",
        version = "0.1.0",
        preamble = PREAMBLE,
        tools = [Greet,],
        namespaces = []
    );
    ```

    The model reads `DESCRIPTION` to decide when to call the tool, so write it as a trigger ("Use when..."), not as a summary of the code. `namespaces = []` means the App asks for no host capabilities such as chain reads or wallet staging. That's right for an App that only calls an external API.
  </Step>
</Steps>

## Build

```bash
cargo build --release
```

```text
Compiling aomi-sdk v5.1.1
Compiling hello-aomi v0.1.0
Finished `release` profile [optimized] target(s) in 12.6s
```

## Commit and push

Deploys run from a clean commit, so keep build output out of git:

```bash
printf '/target\n/.aomi\nCargo.lock\n' > .gitignore
git init && git add . && git commit -m "init hello-aomi"
```

Push to the GitHub repository you'll connect next.

## Deploy and activate

<Steps>
  <Step title="Connect the repository (once)">
    ```bash
    AOMI_BACKEND_URL=https://api.aomi.dev aomi-build connect
    ```

    It prints a URL that installs the Aomi GitHub App on your repo. Install it, then paste back the `installation_id` GitHub shows you. This also saves your activation token.
  </Step>
  <Step title="Dry run">
    ```bash
    AOMI_BACKEND_URL=https://api.aomi.dev aomi-build deploy --dry-run
    ```

    Previews the deployment manifest and runs preflight checks without deploying. Fix anything it flags in `aomi.toml` and run it again.
  </Step>
  <Step title="Deploy">
    ```bash
    AOMI_BACKEND_URL=https://api.aomi.dev aomi-build deploy
    aomi-build deploy status
    ```

    The platform builds the plugin from your commit into a release. A build takes a few minutes. Wait for `status` to report the release ready.
  </Step>
  <Step title="Activate">
    ```bash
    AOMI_APP_ACTIVATION_TOKEN=<your-activation-token> \
    AOMI_BACKEND_URL=https://api.aomi.dev \
      aomi-build deploy activate
    ```

    The backend fetches the release, validates it and loads it. Within a few minutes `greet` is available to the agent in new chats.
  </Step>
</Steps>

## If something fails

<AccordionGroup>
  <Accordion title="SDK version mismatch: plugin=X, host=Y">
    `aomi-run` only loads a plugin built against its own SDK version. For a local run, pin `aomi-sdk` to the version `aomi-run` prints on its first line at startup. For a ship build, pin to the platform's required version from `aomi-build sdk check`. The two can differ.
  </Accordion>
  <Accordion title="aomi-run: command not found">
    You installed with `--features cli` only, which builds just `aomi-build`. Reinstall with `--features cli,dev-runtime`.
  </Accordion>
  <Accordion title="Activation rejects the build">
    Check the `aomi-sdk` pin in `Cargo.toml`. It must be exact (`=x.y.z`) and match `aomi-build sdk check`.
  </Accordion>
</AccordionGroup>
